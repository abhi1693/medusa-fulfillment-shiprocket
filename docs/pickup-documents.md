# Pickup and shipment documents

Researched 2026-11-17 against the official [Shiprocket collection](https://apidocs.shiprocket.in/api/collections/8407119/SzYW1zB2?segregateAuth=true&versionTag=latest) and Medusa 2.22.4 public Fulfillment module/provider contracts. Inspected `client/index.ts`, the tracking pickup/sync routes, tracking module service and native `@medusajs/fulfillment/dist/services/fulfillment-module-service.js#updateFulfillment`.

Pickup requires one shipment ID with an assigned AWB. An HTTP success is insufficient: require `pickup_status: 1`. Retain the carrier's acknowledged date; omit an unspecified request date and let the carrier select an available slot. Read the exact remote shipment binding before scheduling, and reuse an already confirmed pickup on retry. Pickup and Sync serialize through the public Medusa locking service. A durable pending marker prevents replay after an uncertain transport outcome or crash; carrier confirmation resolves it. Explicit rejection allows a later retry. The route does not expose rescheduling; use the carrier dashboard for a deliberate date change.

Generate labels using `shipment_id`, invoices using `ids` (order IDs), and manifests using `shipment_id` after confirmed pickup. Print an already generated manifest using `order_ids` only when the generation response explicitly names this shipment as already manifested. Require semantic success and a nonempty HTTPS URL. Initial fulfillment persists label/invoice URLs and native label records; it defers manifest generation without scheduling pickup. Sync preserves stored URLs on partial failure and updates matching native label entries through the public module service.

Read shipment state separately from tracking activity. `track_status` describes activity availability, not shipment status. Sparse activity responses must preserve dates and scans. Unzoned carrier dates use IST. Manual pickup acknowledgement survives missing activities in fulfillment data. The widget uses the configured SDK and displays missing documents as a retryable carrier outcome.

These public Admin routes require authentication and a consuming authorization policy. A host application can require an order-management capability for pickup and Sync, and a separate order-read capability for tracking. The provider must not infer staff grants from native visibility.

Validation uses offline Axios fixtures plus the consuming app's isolated native and browser suites. No real pickup, booking or cancellation is generated by these tests. A valid URL is not proof of a readable PDF: verify a live document without forwarding API credentials to its document origin. Sandbox label failures and document CDN permissions require carrier-side resolution.
